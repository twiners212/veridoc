## 1. Document Lifecycle State Machine (`CONFIRMED`)

Every SOP consists of a logical **Document** container (e.g., `SOP-SAF-004`) and one or more immutable or working **Document Versions**. Lifecycle states apply at the **Document Version** level.

    PendingApproval --> Approved : All Sequential Steps Approved

    Published --> RETIRED : Manual Retire

Approval Workflow & Sequential Rules2.1 Slice 1: Sequential Approval Engine (CONFIRMED)Ordered Steps (BR-SEQ-01, PROPOSED): Every workflow submitted in Slice 1 defines an ordered sequence of steps (step_order = 1, 2, ..., N), each assigned to a specific user who holds an approval-capable role (Approver / Reviewer, Quality Manager, or Workspace Admin).   Strict Step Gating (BR-SEQ-02, PROPOSED): Only the step with the lowest step_order in PENDING status is active. Approver $N+1$ CANNOT approve or reject until Approver $N$ has completed sign-off.No Duplicate Consecutive Approvers (BR-SEQ-03, PROPOSED): A workflow cannot assign the exact same user to two different steps in the same sequential cycle unless explicitly allowed by an Admin override.Sign-Off Re-Authentication (BR-SIG-01, CONFIRMED / PROPOSED): Approvers MUST re-authenticate immediately prior to executing a sign-off. In Slice 1 (PROPOSED), this is enforced via password re-entry through Better Auth; SAML SSO + WebAuthn MFA is deferred to Slice 3.   Mandatory Sign-Off Metadata (BR-SIG-02, CONFIRMED): Every approval or rejection MUST persist: Full Name, User ID, User Role, Client IP Address, UTC Timestamp, SHA-256 Document Digest, and explicit Sign-off Intent / Reason.   2.2 Slice 2: Deferred Workflow Capabilities (CONFIRMED Deferred — Do NOT Implement in Slice 1)Parallel & Quorum Approvals (REQ-FR-201b, REQ-FR-202): Parallel approval branches and threshold rules (e.g., "Any 2 of 3 Quality Managers").   Delegation Rules (BR-APP-03, REQ-FR-203): Planned temporary delegation of approval authority to a peer with equal or higher RBAC permissions.   Overdue Escalation (REQ-FR-204): Automated reminder at 48 hours of inactivity and optional manager escalation at 96 hours.   3. Critical Governance Invariants3.1 Separation of Duties & Self-Approval Prevention (DEC-03 — VALIDATED, BR-APP-01)Standard Policy (CONFIRMED): An author CANNOT approve their own submitted document version (author_id !== approver_id and submitted_by !== approver_id).   Enforcement Layers:Workflow Submission Guard: Server rejects workflow submission if the sole approver is the document author (unless override is active).Sign-Off Execution Guard: Server explicitly verifies actor.id !== version.author_id inside the sign-off transaction; returns 403 Forbidden (SELF_APPROVAL_PROHIBITED) on violation.Database Constraint (PROPOSED): A BEFORE INSERT OR UPDATE trigger on approval_steps (DATABASE_SCHEMA.md §5.3) prevents inserting or updating an approval record to APPROVED where the actor matches the version author, unless the cycle's allow_self_approval_override snapshot is true.Small-Org Override Exception (CONFIRMED per Spec §9.1): If a Workspace Admin explicitly enables the workspace-level allow_single_author_override flag (disabled by default), self-approval is permitted only when no other eligible approver exists. Every overridden sign-off MUST be tagged self_approval_override = true and emit an explicit SELF_APPROVAL_OVERRIDE_USED audit event (PROPOSED).   3.2 Atomic Approval Invalidation on Edit (DEC-04 — VALIDATED, BR-APP-02)Invariant (CONFIRMED): Modifying any payload element of a document version currently in PENDING_APPROVAL MUST atomically invalidate the active approval cycle.   What Triggers Invalidation (CONFIRMED / PROPOSED):Editing Markdown/Rich-Text body content.   Replacing, adding, or removing the attached PDF binary.   Modifying critical controlled metadata on the version itself (PROPOSED: title, effective_date). `document_code` and `category` live on the `documents` container, not on the version payload, and changing them does NOT trigger invalidation; they are logged as admin metadata changes. There is no `target_audience_rules` column — audience is assigned via groups at publication (REQ-FR-501).   (Non-payload admin fields do NOT trigger invalidation. There is no in-Slice-1 commenting feature; do not invent one.)Mandatory Atomic Transaction Sequence (CONFIRMED):Acquire row lock (FOR UPDATE) on document_versions and active approval_cycles.Verify state is PENDING_APPROVAL.Mark the active approval_cycle as INVALIDATED and mark all prior APPROVED / PENDING approval_steps in that cycle as INVALIDATED (preserving them for audit history—never hard-delete).   Apply the new payload/metadata, increment the draft revision (v0.1 → v0.2), clear the locked submission digest, and set state to DRAFT.   Append an APPROVAL_INVALIDATED_BY_EDIT audit log record containing actor ID, invalidated cycle ID, prior SHA-256 digest, and timestamp.   Commit transaction.3.3 Admin Approver Override (BR-APP-04 — CONFIRMED)Condition: An assigned approver in an active PENDING_APPROVAL step is deactivated or unavailable without delegation.   Rule: Only a Workspace Admin may reassign that pending step to another eligible approver (still honoring BR-APP-01 separation of duties).   Audit Requirement: Must require a written justification and emit an ADMIN_APPROVER_OVERRIDE audit record capturing previous approver, new approver, admin ID, and reason.   4. A Quality Manager or Workspace Admin may flag the revision as a minor administrative edit with a mandatory logged audit justification (BR-VER-03), but the flag does NOT bypass re-approval in Slice 1; the bypass is a post-Slice-1 decision.   4.2 SHA-256 Payload Binding (DEC-06 — PRODUCT DECISION)Upon submission to PENDING_APPROVAL, the server computes a deterministic SHA-256 digest:   Canonical document digest (single source of truth, all files): `document_sha256 = SHA-256(normalized_markdown || file_sha256 || canonical_metadata_json)`, where `normalized_markdown` is the NFC, LF-normalised Markdown text (empty string if PDF-only), `file_sha256` is the SHA-256 of the exact immutable PDF object in Supabase Storage (empty string if Markdown-only), and `canonical_metadata_json` is the deterministic key-sorted JSON `{ document_code, title, version_label, tenant_id }`. This is the same formula stated in SECURITY.md §6 and ARCHITECTURE.md §7.3; “Text Content || Binary Attachments || Canonical Metadata” in Spec §10.2 means exactly this.Canonical Input Construction (PROPOSED):Text Content: UTF-8 normalized (NFC) Markdown string with LF (\n) line endings (empty string if PDF-only).Binary Attachments: Raw byte stream (or pre-computed SHA-256 of the exact immutable PDF object stored in Supabase Storage).Canonical Metadata: Deterministic key-sorted JSON string containing { document_code, title, version_label, tenant_id }.Binding Rules (CONFIRMED):Every approval_steps sign-off record stores the document_sha256 that was presented to and approved by the approver.   Every read_acknowledgments record stores the document_sha256 of the published version acknowledged by the reader.   Before accepting any sign-off or publication, the server recomputes or verifies the stored digest against the active version payload; any mismatch aborts the transaction and logs INTEGRITY_HASH_MISMATCH (PROPOSED).5. Publishing & Read Acknowledgment Rules5.1 Publishing Rules (CONFIRMED)Only Workspace Admin and Quality Manager roles can publish an APPROVED version.   Publishing immediately (or when effective_date <= NOW()) atomically:Transitions the new version to PUBLISHED.Transitions any previously PUBLISHED version of the same Document to SUPERSEDED.   Expands configured Target Audience Rules (Department, Site Location, Job Role, or Custom User Groups) into concrete read_assignments records with a due_at deadline (e.g., 7 days from publication).   5.2 Read Acknowledgment Rules (CONFIRMED)Target Resolution (PROPOSED): Assignments are materialized per user at publication time. If a new user joins an assigned group while the SOP is PUBLISHED, a background or sync job assigns the active SOP to them (PROPOSED).Engagement Gate (CONFIRMED / PROPOSED): The reader viewer tracks scroll depth / page view progress and viewing duration before enabling the acknowledgment button. Default PROPOSED threshold: scrolled >= 90% of content (or viewed final PDF page) AND spent >= 10 seconds on the document.   Binding Action (CONFIRMED): Clicking "I Acknowledge That I Have Read & Understand This SOP" executes a server-side mutation storing user_id, acknowledged_at (UTC), document_version_id, and document_sha256, and appends a READ_ACKNOWLEDGED audit entry.   Idempotency (PROPOSED): A user can only acknowledge a specific (document_version_id, user_id) pair once (enforced via UNIQUE database constraint).6.
