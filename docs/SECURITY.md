## 1. Security Posture & Compliance Boundaries (`CONFIRMED`)

### 1.1 Supported Governance Alignment
The platform implements technical controls that assist mid-market organizations in meeting document control requirements for **ISO 9001**, **ISO 27001**, **SOC 2 Type II**, and **GMP** guidelines.

### 1.2 Explicit Non-Claims & Boundaries (`DEC-02`, `DEC-08`)
* **No Out-of-the-Box FDA 21 CFR Part 11 Compliance (`DEC-02` — `DISPROVEN`):** The MVP does **not** claim universal or out-of-the-box FDA 21 CFR Part 11 compliance. Achieving Part 11 compliance requires customer-specific IQ/OQ/PQ validation protocols, operational SOPs, two-component/biometric electronic signatures, and deferred Slice 3 capabilities.
* **No eIDAS QES:** The platform does **not** provide legally binding Qualified Electronic Signatures (QES) under eIDAS without third-party PKI integration.
* **Audit Trail Immutability Boundaries (`DEC-08` — `PARTIALLY VALIDATED`):** Audit records are protected against application-level and standard workspace-admin tampering via append-only PostgreSQL models, `REVOKE` permissions, triggers, and cryptographic hash chaining. The system MUST NEVER be described as "100% unalterable" or universally tamper-proof; infrastructure-level cloud/DBA superuser overrides remain governed by platform IAM and database administrator controls.

### 1.3 Core Security Principle
**Client-side validation, UI button disabling, and client-held state are NEVER security boundaries.** Every authorization check, separation-of-duties rule, state transition guard, `SHA-256` verification, and tenant filter MUST be enforced server-side and reinforced at the PostgreSQL layer.

## 2. Threat Model (`PROPOSED`)

| Threat ID | Category (STRIDE) | Threat Scenario | Impact | Primary Mitigations (Slice 1) |
| :--- | :--- | :--- | :---: | :--- |
| **TH-01** | Information Disclosure | **Cross-Tenant Data Leakage:** Authenticated user in Tenant A accesses Tenant B's SOPs, audit logs, or signed storage URLs via ID guessing or missing `WHERE` clause. | Critical | Mandatory `withTenantContext()` wrapper (`SET LOCAL app.current_tenant_id`), forced PostgreSQL RLS on `app_user` (`NOBYPASSRLS`), composite `(tenant_id, id)` FKs, `404` anti-enumeration responses. |
| **TH-02** | Elevation of Privilege | **Self-Approval Bypass (`DEC-03`):** Document Author manipulates request payloads or assigns themselves to approve their own SOP. | High | Server-side `BR-APP-01` policy check (`actor.id !== version.author_id`) + PostgreSQL `BEFORE INSERT OR UPDATE` trigger on `approval_steps` + audited `allow_single_author_override` disabled by default. |
| **TH-03** | Tampering | **Mid-Approval Bait-and-Switch (`DEC-04`):** Author silently alters SOP text or replaces PDF after Approver 1 signs off but before Approver 2 signs off. | Critical | Atomic `FOR UPDATE` invalidation transaction (`BR-APP-02`) resets version to `DRAFT` and marks prior approvals `INVALIDATED`[cite: 1, 2]; `SHA-256` payload binding (`DEC-06`) verifies exact digest at sign-off[cite: 1, 2]. |
| **TH-04** | Tampering | **Post-Publication Alteration (`BR-VER-02`):** Malicious actor or bug mutates content or digest of a `PUBLISHED` SOP. | Critical | Immutable versioned Supabase Storage keys + PostgreSQL trigger blocking content/digest updates once state is `APPROVED`/`PUBLISHED`/`SUPERSEDED`/`RETIRED`. |
| **TH-05** | Repudiation | **Sign-Off Repudiation / Unattended Session Abuse:** Someone clicks "Approve" on an approver's unlocked laptop, or an approver denies signing. | High | Mandatory password re-authentication at sign-off (`REQ-FR-401`, `BR-SIG-01`) + immutable capture of Full Name, User ID, Role, IP, UTC timestamp, `SHA-256` digest, and explicit intent (`REQ-FR-402`). |
| **TH-06** | Tampering / Repudiation | **Audit Log Deletion or Backdating (`DEC-08`):** Compromised app account attempts to delete or edit audit entries[cite: 1, 2]. | High | `REVOKE UPDATE, DELETE ON audit_logs FROM app_user` + `BEFORE UPDATE OR DELETE` trigger + per-tenant serialized `SHA-256` hash chain with monotonic `sequence_number`. |
| **TH-07** | Tampering / Spoofing | **Malicious File Upload / Stored XSS:** Attacker uploads disguised HTML/JS as `.pdf` or injects `<script>` into Markdown SOP content. | High | Server-side `%PDF-` magic-byte check, 50MB cap, private bucket with `Content-Disposition` / non-executable headers, strict Markdown allow-list sanitization, and CSP headers. |
| **TH-08** | Denial of Service | **Race Condition / Brute-Force Abuse:** Concurrent sign-off + edit race corrupts workflow state, or attacker brute-forces sign-off re-auth passwords. | Medium | PostgreSQL row-level locking (`FOR UPDATE`), partial unique indexes (`uq_one_published_version_per_doc`, `uq_one_active_cycle_per_version`), and per-IP/per-user rate limiting. |

## 4. Multi-Tenant Isolation & Supabase RLS (`CONFIRMED` / `PROPOSED`)

### 4.1 Database-Level Isolation Enforcement
* **Dedicated Non-Bypass Role (`PROPOSED`):** The application connects via `DATABASE_URL` using a restricted PostgreSQL role (`app_user`) created with `NOBYPASSRLS`. Never use the Supabase `postgres` superuser or `service_role` database credential for runtime application queries.
* **Forced RLS (`PROPOSED`):** Every tenant-scoped table enables both `ENABLE ROW LEVEL SECURITY` and `FORCE ROW LEVEL SECURITY` with:
  ```sql
  USING (tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid)
  WITH CHECK (tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid)
Transaction-Scoped Context (PROPOSED): withTenantContext(session, fn) wraps every tenant query in BEGIN ... COMMIT and calls SELECT set_config('app.current_tenant_id', $1, true) (is_local = true). When the transaction finishes, PostgreSQL automatically clears the setting before returning the connection to Supavisor/PgBouncer, preventing cross-request tenant bleeding.Fail-Closed Guarantee: Any query executed outside withTenantContext() sees app.current_tenant_id = NULL, returning zero rows and failing all inserts/updates.5.
