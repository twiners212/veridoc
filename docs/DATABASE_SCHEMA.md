# VeriDoc — Database Schema Specification

> **App name:** VeriDoc — Document & SOP Approval Workspace. “VeriDoc” is the canonical product name throughout this package.

> **Status:** Slice 1 (Core Lifecycle MVP) — Database Baseline  
> **Database Engine:** Supabase PostgreSQL 15+ (`PROPOSED` Stack Baseline)  
> **ORM:** Drizzle ORM (`src/db/schema/`)  
> **Related Docs:** `docs/ARCHITECTURE.md`, `docs/BUSINESS_LOGIC.md`, `docs/SECURITY.md`, `docs/API_SPECIFICATION.md`

---

## 1. Schema Design Principles (`PROPOSED`)

1. **Logical Multi-Tenancy with Hard RLS:** Every workspace-owned table includes a non-null `tenant_id` column and enforces PostgreSQL Row-Level Security (RLS) via transaction-scoped `current_setting('app.current_tenant_id', true)`.
2. **Cross-Tenant Foreign Key Immunity:** Parent tables expose `UNIQUE (tenant_id, id)` so child tables reference `(tenant_id, parent_id)`, making cross-tenant joins or orphaned references impossible at the schema level.
3. **Immutable Audit & Version History:** Published/Superseded/Retired document versions, approval sign-offs, read acknowledgments, and audit logs are never hard-deleted or silently overwritten.
4. **Database-Level Invariants:** Critical rules—such as single active `PUBLISHED` version per document (`BR-VER-01`), unique read acknowledgment per `(version, user)` (`BR-ACK-01`), and append-only audit logs (`DEC-08`)—are enforced by PostgreSQL indexes, `CHECK` constraints, and triggers in addition to application services.
5. **Slice 1 Discipline:** Tables and columns strictly cover Slice 1 MVP. Slice 2 (parallel/quorum branches, delegation tables, escalation schedules) and Slice 3 (SAML/SCIM, webhooks) are excluded from MVP migrations.

Tenant Isolation & Database-Level Security (CONFIRMED / PROPOSED)5.1 Dedicated Application Role (PROPOSED)Runtime queries from Next.js / Drizzle connect as PostgreSQL role app_user (NOBYPASSRLS).Schema migrations connect via DIRECT_DATABASE_URL as the migration owner role.app_user is granted SELECT, INSERT, UPDATE, DELETE on operational tables, except: UPDATE and DELETE are explicitly revoked on audit_logs and read_acknowledgments, and DELETE is explicitly revoked on approval_cycles, approval_steps, document_versions and read_assignments (AGENTS.md §8 prohibits hard-deleting these rows):SQLREVOKE UPDATE, DELETE ON TABLE audit_logs FROM app_user;
REVOKE UPDATE, DELETE ON TABLE read_acknowledgments FROM app_user;
REVOKE DELETE ON TABLE approval_cycles, approval_steps, document_versions, read_assignments FROM app_user;
5.2 Row-Level Security (RLS) Policy Template (PROPOSED)Enabled and forced (ENABLE ROW LEVEL SECURITY + FORCE ROW LEVEL SECURITY) on every tenant-scoped table (tenants, tenant_memberships, audience_groups, audience_group_members, documents, document_versions, approval_cycles, approval_steps, read_assignments, read_acknowledgments, audit_logs):SQLALTER TABLE document_versions ENABLE ROW LEVEL SECURITY;
ALTER TABLE document_versions FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation_policy ON document_versions
  FOR ALL
  TO app_user
  USING (tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid)
  WITH CHECK (tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid);
Fail-Closed Behavior: If a bug omits withTenantContext(), current_setting('app.current_tenant_id', true) returns NULL, causing RLS to return zero rows and block all writes.5.3 Database Triggers for Critical Invariants (PROPOSED)Append-Only Audit Trail Trigger (DEC-08): A BEFORE UPDATE OR DELETE trigger on audit_logs raises an exception (AUDIT_LOG_IMMUTABLE) as defense-in-depth beyond REVOKE permissions. (Note: per DEC-08, infrastructure superusers remain governed by cloud platform IAM controls.)   Published Version Immutability Trigger (BR-VER-02): A BEFORE UPDATE OR DELETE trigger on document_versions blocks any modification to title, markdown_content, file_storage_key, file_sha256, or document_sha256 once OLD.lifecycle_state IN ('APPROVED', 'PUBLISHED', 'SUPERSEDED', 'RETIRED'), permitting only valid lifecycle state transitions (APPROVED -> PUBLISHED -> SUPERSEDED/RETIRED).Self-Approval Prevention Trigger (DEC-03, BR-APP-01): A BEFORE INSERT OR UPDATE trigger on approval_steps verifies when NEW.status = 'APPROVED' that NEW.acted_by_user_id <> document_versions.author_id unless approval_cycles.allow_self_approval_override = true[cite: 1, 2]. Join path (defined here, not left implicit): approval_steps.approval_cycle_id → approval_cycles.id → approval_cycles.document_version_id → document_versions.id → document_versions.author_id. An INSERT that already sets status='APPROVED' with the author as actor is blocked the same way as an UPDATE.6.
